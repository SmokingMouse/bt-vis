# 2026-05-27: bt-vis 整体架构决策

## Context

新项目：可视化 BitTorrent 通信流程的交互式 demo。原始 idea 列了 4+ 角度（存量请求、增量、异常鲁棒性、冷启动……）。脑爆阶段需要把模糊 idea 收敛成可执行方案。

关键背景约束：
- 定位是 Portfolio / 面试可演示项目（不是个人学习用、不是博客配图、不是完整教学沙盒）
- 用户技术栈偏向 Python + React/Next.js + Tailwind
- 用户作风偏向激进打透单点，不喜分散
- 2-3 周时间盒

## Decision

**采用「全前端 TS sim engine + 5 段场景 + 全流程模式」方案**，主线讲"一个新节点从加入 swarm 到变成 seeder 的全过程"。

具体决策点：

1. **场景范围**: 存量请求 + 冷启动（合并为一条主线），明确放弃增量、异常、wire 协议兼容
2. **实现形态**: 全前端 TS sim engine + 可控时间轴（不做后端，不做真实多进程）
3. **协议层次**: 协议为"示意级"——保留语义（rarest-first、tit-for-tat 等），不追求 BEP 字节级合规
4. **场景结构**: 5 段独立小场景（Discovery / Handshake / Selection / Choking / Seeding）+ 1 个全流程模式
5. **节点规模**: 默认 6-8 peer
6. **打磨深度**: 能发出去的作品级别（视觉过得去、链接能直接玩、README 讲技术决策）
7. **推进方式**: 3 周垂直切片，每周末有可演示状态

## Rationale

**为什么是 Portfolio 定位**：用户主动选择，不是教学也不是学习用。这反向约束了"必须能部署 + 必须有打磨"。

**为什么聚焦存量+冷启动**：4 个角度都做，每个都浅 → Portfolio 大忌；"节点从加入到 seeder" 是一条天然贯穿多机制的主线（discovery / handshake / piece selection / choking / seeding 都顺势出场），讲故事的密度最高。

**为什么是全前端 sim**：
- 部署纯静态（Vercel/GH Pages），链接发出去直接玩——Portfolio 命门
- 可控时间轴 = 看的人能停在任意一帧理解
- 协议引擎 + UI 分离 = "前端写协议状态机" 本身就是技术展示

**为什么 5 段 + 全流程**：单场景 8-10 分钟看完体力消耗大；5 段独立可玩允许按兴趣跳转，全流程模式作为"完整成品演示"。

**为什么 sim 与 UI 完全分离**：engine 纯函数式 + tick-based deterministic（seed + scenario → 同样结果）→ 单测容易、时间轴回放安全、未来换 UI 不影响协议逻辑。

## Alternatives considered

**A. 受众选不同方向**（rejected）
- "技术博客配图"：多段独立 GIF 缺乏交互、不能当 Portfolio
- "交互教学沙盒"：工作量太大、超 2-3 周时间盒
- "自己边做边学"：缺打磨动力、产出可能停在 50%

**B. 范围选不同组合**（rejected）
- "增量+鲁棒性"：技术深但缺一个起点状态作为参照，看的人难入戏
- "全四场景拼"：典型 Portfolio 反模式——拼凑感强，主线断
- "单场景极致打磨"：缺 P2P 协议最有意思的"加入/退出"那一面

**C. 形态选不同实现**（rejected）
- "Python 后端跑真节点 + 前端回放"：部署复杂、用户交互弱、portfolio 不需要"真"到这种程度
- "WebSocket 实时多节点"：状态不可重现、看的人每次看到不一样反而坏；部署复杂；最不适合 portfolio
- "混合 TS sim + Rust toy 实现"：工作量翻倍，超时间盒

**D. 时间盒选不同**（rejected）
- "1 周 MVP"：缺打磨深度，Portfolio 不达标
- "1-2 月极致打磨"：拖久了黑洞风险高，用户多项目并行的工作模式不匹配

## Consequences

**已知影响**：
- 必须 day 1 就把 engine 设计成 deterministic + 可序列化 state，否则 Week 2 加时间轴拖动会撞墙（R3）
- Week 2 视觉打磨硬截止 D12-13，超出就回退"够用就行"（避免 R2 黑洞）
- 五段场景的"注释/旁白"内容用图标 + 短 tag，不写长段文字（避免 R4）

**风险**：
- Choking 算法状态机复杂度可能被低估 → Week 2 头两天专攻
- 前端视觉打磨吞时间 → 调用 frontend-design skill 出方案而非自己琢磨配色

**deferred 的方向**（明确推后，不在 MVP 中）：
- 增量场景（新节点动态加入、新资源进入 swarm）
- 异常/鲁棒性（恶意 peer、网络分裂、Sybil）
- 真实 BT wire 协议字节级兼容
- 移动端适配

未来回看这个决策的判断标准：如果 Week 2 中期发现"5 段场景"信息密度不够、看的人记不住 → 重新评估是否要砍到 3 段。
